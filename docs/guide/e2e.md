# Browser e2e suite

- Commands: `npm run e2e` (projects `desktop` and `phone`), `e2e:smoke` (`@smoke`), `e2e:ui`, one spec with `npm run e2e -- <file or -g title>`. It needs the API JAR of a backend checkout at `../backend` (`mvn -DskipTests package` there) or `GLAZELAB_E2E_JAR`, builds the frontend and starts its own API (dev profile, fresh H2, mail-free, rate budgets × 100) and web server on free ports 40000–49999; it never touches a dev server or real data.
  - Outputs: everything goes under `GLAZELAB_E2E_HOME` (default `glazelab-e2e` in the OS temp folder); a suite run writes `suite/` there (or `GLAZELAB_E2E_OUTPUT`): builds, the API's data and log, traces, screenshots, the HTML report (`npx playwright show-report <output>/report`). Workers: `GLAZELAB_E2E_WORKERS` (number or percentage, default 4).
  - Browser: `CHROME_BINARY`, else `/usr/bin/chromium-browser` or `/usr/bin/chromium`, else Playwright's own (`npx playwright install chromium`, the version the pinned Playwright supports).
- `e2e/` is type-checked by `npm run check` (`e2e/tsconfig.json`) and formatted by Prettier: `playwright.config.ts` (projects `desktop` 1280 × 800 and `phone` 390 × 844 touch, retries 0, service workers blocked unless a test allows them), `global-setup.ts` (URLs reach the workers through `GLAZELAB_E2E_*` env vars), `support/` (servers, the `Api` seeding client over the page's cookies, `mockApi`, `t()` over `en.json`, generators, page objects in `support/pages/`), `specs/*.spec.ts`.
- `specs/core-features.spec.ts` is the `@smoke` gatekeeper (the core journey, every step asserted): run it after UI or API changes and keep it fast. It uses the `Pace` helper (`support/pace.ts`), which acts at once unless `E2E_VIDEO=1`; only `walkthrough.config.ts` (`npm run e2e:walkthrough`, the phone clip in `walkthrough/` under `GLAZELAB_E2E_HOME` or `GLAZELAB_WALKTHROUGH_OUT`; needs ffmpeg) sets that.
- `e2e/walkthrough/` holds the page videos (`npm run e2e:videos [-- <spec>]`; MP4s in `videos/` under `GLAZELAB_E2E_HOME` or `GLAZELAB_VIDEOS_OUT`, seed kept in `videos-seed/` until `GLAZELAB_VIDEOS_RESEED=1`; needs ffmpeg and ffprobe): one spec per page on an emulated iPhone X, seeded by `seed.ts`, recorded by `support.ts` (screenshots at device pixels, not Playwright's video). A new page or feature gets a beat in its spec, and the seed stays valid against the API contract.
- Tests import `test`/`expect` from `support/test.ts`. Fixtures: `uid` (unique per test and project; put it in every title, address, code and search), `account`/`signedIn` (a fresh account; never share one), `newApi()` (another person), `shell`, `encoder`. An uncaught page error or CSP violation fails the test.
- Seed through `Api`, assert through the UI.
- Specs run in English; other languages only where the language is the subject (`language.spec.ts`, `overflow.spec.ts`, the language block of `a11y.spec.ts`): dictionaries are checked by Vitest.
- Selectors by role, label or text from `t('<key>')` (`startsWith`, `withCount` for composed names), never CSS classes; repeated steps go into a page object or helper.
- One behaviour per test, named for it; tag the quick path `@smoke`. No sleeps or fixed waits: web-first assertions and `expect.poll`. A viewport-specific test skips the other project with the reason.
- The app never gets a test-only hook. States the API cannot produce on demand (changed terms, server failures) come from `mockApi` (`page.route`, which a service worker would bypass: keep workers blocked there; its sync answers `resync` with an empty paged listing).
- Smaller sync pages come from rewriting the `limit` of `GET /api/sync/combinations` in `page.route` (`specs/sync.spec.ts`); a delta refresh is triggered by a network change (`context.setOffline`).
- Camera scans: a spec that scans sets `launchOptions` at its top level (a worker of its own) with `--use-fake-device-for-media-stream --use-file-for-fake-video-capture=<file>` of `barcodeVideo(code)` (`support/barcodes.ts`, written under `FIXTURES`) and `permissions: ['camera']`. Never grant the camera without the fake file (`specs/shelf-scan.spec.ts`).
  - Reset a reused capture file to `barcodeVideo(null)` before cases that do not decode, so a previous case's jar cannot open a sheet or form during a focus check.
  - Headless Chromium keeps every page visible (also behind another tab, and `Page.setWebLifecycleState` does not freeze a page using the camera): a hidden page is an overridden `document.visibilityState` plus a dispatched `visibilitychange`; track states come from a test-side `getUserMedia` wrapper in `addInitScript` (`specs/camera-pause.spec.ts`).
- Site admins: the API has no endpoint that makes one, so `support/site-admin.ts` `grantSiteAdmin(email)` runs `UPDATE app_user SET site_admin = TRUE WHERE lower(email) = lower(…)` through the H2 shell on the suite's own database; the account's next request sees the flag.
  - `startBackend` opens the database with `AUTO_SERVER=TRUE` (`SPRING_DATASOURCE_URL`) and starts the JVM with `-Dh2.bindAddress=127.0.0.1`. Keep it: without it the lock file names the host's network address, and a changed Wi-Fi address mid-run fails every later admin test with `Connect timed out`.
  - The H2 jar is unpacked from the API JAR with `unzip`, else taken from `~/.m2`.
  - The API's `api.log` under the run's `backend/` keeps every SQL error with its cause chain (`org.hibernate.orm.jdbc.error` at DEBUG), for flaky registrations and the like.
- Firefox: `GLAZELAB_E2E_FIREFOX=1 npm run e2e -- --project=firefox <spec>` adds a `firefox` project (the system `/usr/bin/firefox` or `FIREFOX` over WebDriver BiDi, `channel: 'moz-firefox'`; desktop width, fine pointer); never part of the default run. Playwright's screenshot (also on failure) injects a `<style>` that the CSP blocks, so a Firefox test that takes one fails on that report.
- The suite's database is shared by every test of a run:
  - A test that reads a queue gives its people names with its `uid` and filters by it.
  - Never expect a seeded item in a list cut to the newest few of shared data (Studio's waiting list of five): other tests' newer items push it out.
  - A picture that an admin may remove comes from `support/images.ts` `seededPicture(seed)`: a removal blocks the picture and its close copies for every later upload of the run, both projects included.
- The app reads its lists on load: after seeding through another account's `Api`, a test reloads (`page.goto('about:blank')` first, since a `goto` that differs only in the hash does not reload) or navigates to a page that fetches on mount (the account and club pages re-read the buddy lists).

Gotchas:

- `test.use()` is file-wide even on an extended test object: a service-worker test goes in its own `describe` with its own `use({ serviceWorkers: 'allow' })`. A file-level `use` silently allows workers for every test of the file and fills Cache Storage with the worker's entries.
- The API encodes one image at a time and answers 503 to a parallel upload, so every upload (seeding, upload dialog) runs under `withEncoder`/the `encoder` fixture.
  - The lock is not re-entrant: a test that seeds with an `Api` upload (`api.uploadAvatar` included) must not also request the `encoder` fixture. `specs/avatar.spec.ts` presses Save through `AvatarSection.send()`, which wraps just that click in `withEncoder`.
- A large file goes to `setInputFiles` by path (a sparse file under `FIXTURES`, `specs/avatar.spec.ts` `sparseFile`), never as a buffer: a buffer passes the browser protocol and takes tens of seconds on a loaded host.
- A scan that decodes may close its scanner before a preview check runs: wait for the preview or what the code opens (`.or(…).first()`).
- Cookies ignore ports, so a second web server (`startWebServer`, as the update spec uses for its own service worker) shares the session of `page.request`.
- The footer sits inside `<main>`, so it is no `contentinfo` landmark.
